# qixidi-web-admin 开发需求与设计

> 管理后台 2.0 · Nuxt 3 重写版。本文档是新后台唯一的需求源，旧后台（qixidi-web-admin-1.0）仅作交互参考，不再照搬其模块。

---

## 1. 背景与目标

### 1.1 为什么重写

| 旧后台（qixidi-web-admin-1.0） | 新后台（本项目） |
|------|------|
| Vue 2 + Element UI（RuoYi 体系），技术栈停止演进 | Nuxt 3 + Vue 3 + TS + Naive UI，与门户（qixidi-web-nuxt3）同栈 |
| 完整 RBAC：角色/菜单/部门/岗位/字典/通知等 17 张 sys 表 | 登录即管理员，权限模型最小化 |
| 页面按 RuoYi 生成器模板铺开，大量模块用不上 | 只做核心需求，按本文档分期交付 |

### 1.2 目标

1. **单人可运维**：站长一人使用，无多角色协作诉求，砍掉角色/菜单权限体系
2. **同栈降本**：与门户共用一套技术心智（Naive UI / Pinia / Tabler 图标 / Tailwind）
3. **核心闭环**：登录 → 看数据 → 管文章 → 管评论 → 管用户 → 改站点配置

### 1.3 难度评估（结论）

| 部分 | 难度 | 说明 |
|------|------|------|
| 前端骨架（本项目） | ⭐⭐ 低 | 已完成：模板落地 + 布局壳 + 路由守卫 + 请求层，无头验证全绿 |
| P0 五个页面 | ⭐⭐⭐ 中 | 均为列表 + 操作类页面，后端接口已存在，逐个对接即可 |
| 后端 sys 表瘦身 | ⭐⭐⭐⭐ 中高 | 涉及 11 张 RBAC 表废弃 + `@SaCheckPermission` 改造 + 菜单驱动的登录链路（getInfo/getRouters）剥离，需保证登录链路不断 |
| 生产切换 | ⭐⭐⭐ 中 | 新旧后台并存验证 → nginx 切流量 → 归档旧后台 |

**关键风险**：登录链路。现 `POST /login` → `getInfo`（回角色/权限集合）→ `getRouters`（回菜单树）是 RuoYi 套路，新后台静态路由不再调 getRouters，但 getInfo 里的角色集合若是空数组和 `@SaCheckPermission` 有耦合，瘦身时必须同步改造（见 §5.3）。

## 3. 核心需求（P0 —— 第一期必做）

### P0-1 登录对接

**后端接口（已确认，qixidi-service）**：
- `GET /captchaImage` → `{img, uuid}`（base64 图片）
- `POST /login`，`@RequestBody {username, password, code, uuid}` → `data.token`
- `GET /getInfo`（SysLoginController）→ 用户信息（瘦身前含 roles/permissions，瘦身后再定字段）

**要点**：验证码开关后端可配（captchaEnabled），前端读响应决定是否显示验证码输入框；登录成功 `saveToken` 后跳 `/`。

### P0-2 数据看板（pages/index.vue）

**后端接口（已确认）**：
- `GET /business/stat/data/info` —— 综合统计
- `GET /business/stat/data/the/info` —— 指定时段统计
- `GET /business/stat/data/label/data` —— 标签维度数据

**范围**：数字卡片（文章/评论/用户/浏览量）+ 近 30 天趋势图（ECharts 按需引入）+ 标签分布。**不做**：地图、实时大屏。

### P0-3 文章管理（pages/article/index.vue）

**后端接口（已确认）**：`/business/article/information`（ArticleInformationController，列表为 TableDataInfo 分页）

**范围**：
- 列表：搜索（标题/状态）、状态筛选（审核中/已通过/已拒绝）、分页
- 操作：通过 / 拒绝（审核）、下架；**不做**后台新建文章（发稿走前台用户端）

### P0-4 评论管理（pages/comment/index.vue）

**后端接口（已确认）**：`/business/article/comment`（ArticleCommentController）

**范围**：列表 + 删除（含子评论级联确认）+ 屏蔽词命中高亮。**不做**：回复评论。

### P0-5 前台用户（pages/user/index.vue）

**后端接口（已确认）**：`/system/tripartite/user`（TripartiteUserController）

**范围**：列表（昵称/注册时间/最近活跃）、禁用 / 启用。**不做**：改密、代用户操作。

## 5. sys 表瘦身方案（后端改造，与前端并行）

### 5.1 保留（6 张）

| 表 | 用途 | 消费方 |
|----|------|--------|
| `sys_user` | 管理员账号（唯一） | 登录链路 |
| `sys_config` | 站点配置键值 | P1-2 |
| `sys_logininfor` | 登录日志 | P1-3 |
| `sys_oper_log` | 操作日志 | P1-1 |
| `sys_oss` | OSS 文件记录 | P2-2 |
| `sys_black_list` | IP 黑名单 | P2-1 |

### 5.2 废弃（11 张，DDL 归档脚本择机执行）

`sys_role`、`sys_menu`、`sys_dept`、`sys_dict_type`、`sys_dict_data`、`sys_post`、`sys_notice`、`sys_role_menu`、`sys_role_dept`、`sys_user_post`、`sys_user_role`

**执行方式**：先出 `sql/archive-sys-rbac.sql`（RENAME 成 `_deprecated_` 前缀而非直接 DROP，观察一版后清理），生产执行时机 = 新后台 P0 验收通过之后。

### 5.3 代码改造点（qixidi-service）

1. **登录链路**：`SysLoginController.getInfo` 剥离 roles/permissions 计算；`getRouters` 直接废弃（新后台静态路由）
2. **权限注解**：全仓 `@SaCheckPermission` 逐个评估——后台接口改为 `@SaCheckLogin`（登录即管理员）或保留注解但权限集合固定返回 `["*"]`（改动最小，**推荐起步方案**）
3. **实体清理**：qixidi-auth 的 SysRole/SysMenu/SysDept/SysDictType/SysDictData、qixidi-system 的对应 Service/Mapper/XML 同步删除，`mvn clean compile` 验证
4. **字典**：若有业务读 sys_dict（枚举类文字），先 grep 确认依赖点再决定是否以常量枚举替代

### 5.4 前端配合

新后台已按"登录即管理员"设计：静态菜单、无权限指令、无角色切换——后端瘦身对新前端**零影响**，两端可并行开发。

## 6. 非目标（明确不做）

- ❌ 多角色 / 细粒度按钮权限（无场景）
- ❌ 菜单表驱动的动态路由
- ❌ 后台发稿 / 富文本编辑（发稿在前台用户端）
- ❌ 部门树 / 岗位管理
- ❌ 移动端适配（后台桌面优先，≥1280px）
- ❌ SSR（全 CSR）

### 7.1 M1 开工准备（新会话从这里续接）

1. **启动依赖**：后端 qixidi-service 跑在 `127.0.0.1:9001`；前端 `pnpm dev`（3000 端口，devProxy `/api` 已配）
2. **P0-1 注意**：sys 瘦身（M3）未做前，登录走现有 RuoYi 链路——`POST /login` 只取 `data.token`；`GET /getInfo` 返回里含 roles/permissions（RuoYi 遗留），**前端忽略这两个字段**，只存 userId/nickName/avatar 等基本信息，瘦身落地后无需改前端
3. **每页开工前**：先 grep 对应 Controller（见文末速查表）确认参数与返回字段，禁止凭记忆扩写
4. **验证方式**：无头脚本参考 `%TEMP%\qixidi-pptr\verify-admin-skeleton.cjs`（puppeteer-core + Edge，waitForSelector 等 CSR 渲染）；dev server 测完立即关（项目规则）
5. **登录态注入**（admin 页无头验证）：本项目 pinia persist 用 **localStorage**（key=`admin`），直接 `localStorage.setItem('admin', JSON.stringify({token, adminInfo:null}))` 后刷新即认证
