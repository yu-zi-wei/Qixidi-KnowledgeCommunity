# 代码基础规范

通用编码规范，适用于前端和后端开发。

---

## 命名规范

### 原则
命名必须清晰表达意图，拒绝无意义命名（如 `a`, `b`, `temp`）。

### 前端（TypeScript/Vue）
- **变量/常量**：camelCase（`dataList`, `isLoading`）
- **组件**：PascalCase（`DataList.vue`, `UserAvatar.vue`）
- **Composables**：camelCase + use 前缀（`useDataApi.ts`）
- **类型定义**：PascalCase（`DataTypes.ts`）
- **方法/函数**：camelCase，动词开头（`fetchDataList()`, `validateForm()`）

### 后端（Java）
- **类**：PascalCase（`DataService`）
- **接口**：PascalCase + I 前缀（`IDataService`）
- **方法**：camelCase，动词开头（`getDataList()`, `validateData()`）
- **常量**：UPPER_SNAKE_CASE（`MAX_COUNT`）
- **变量**：camelCase（`dataList`, `isLoading`）

## 注释规范

### 需要注释
- 复杂的业务逻辑
- 不明显的算法
- 临时解决方案（标注 TODO）
- 公共 API

### 不需要注释
- 显而易见的代码
- 变量声明（命名应该自解释）

### TODO 格式
```
// TODO: [具体任务]
// TODO: [作者名] [日期] [具体任务]
```

## 错误处理

### 前端
- 统一使用 `useApi` 封装的错误处理
- 必须检查 `error.value` 并处理

### 后端
- 使用业务异常：`BusinessException`、`SystemException`
- 禁止返回 null 表示错误
- 禁止随意抛出通用异常：`RuntimeException`

---

## 类型安全

### TypeScript
- 启用严格模式
- 明确类型声明，不过度依赖类型推断
- 避免使用 `any`，优先使用具体类型或 `unknown`

### Java
- 使用泛型确保类型安全
- 避免使用原始类型（raw types）

---

## 代码复用

### 原则
- 优先复用现有方法或组件
- 抽取重复逻辑
- 不重复造轮子

### 检查清单
编写新代码前，先检查是否已有可复用的实现。

---

## 性能考虑

### 前端
- 使用 `computed` 缓存计算结果
- 避免不必要的重渲染
- 清理副作用（`onUnmounted`）

### 后端
- 禁止在循环中调用数据库
- 使用批量查询
- 合理使用缓存

---

## 代码格式化

- **前端**：ESLint + Prettier
- **后端**：Checkstyle + Google Java Format

提交代码前必须运行格式化。

## 问题诊断与协作

### 遇到复杂问题时主动提问

**原则**：当遇到模糊或多次尝试未解决的问题时，**主动向用户提问**，而不是盲目尝试各种方案。

#### 提问时机

满足以下任一条件时，应该主动提问：
1. 尝试了 3 次或更多方案仍未解决
2. 问题的描述不够清晰，有多个可能的方向
3. 用户提到"偏移"、"闪烁"、"异常"等主观描述
4. 涉及 SSR/客户端水合、性能优化等复杂场景

#### 提问模板

```markdown
我发现 [问题现象]，为了更精确地定位问题，请帮我回答以下问题：

1. **登录状态**：已登录还是未登录？
2. **影响范围**：哪些元素受影响？（具体说明）
3. **偏移方向**：向左、向右、向上、向下？
4. **偏移距离**：大概多少像素？
5. **出现时机**：
   - 刷新后立即出现，然后回正？
   - 刷新后有一个短暂的状态变化？
   - 一直偏移，不会回正？
6. **浏览器环境**：哪个浏览器？是否缩放了页面？
7. **是否可复现**：每次刷新都出现，还是偶尔出现？
8. **其他线索**：是否有控制台错误？网络请求异常？
```

#### 典型场景示例

**场景 1：布局偏移问题**
- 错误：盲目尝试字体加载、滚动条、各种 CSS hack
- 正确：提问确认偏移的元素、方向、距离、时机

**场景 2：功能异常**
- 错误：猜测可能是接口问题、状态管理问题
- 正确：提问确认操作步骤、预期行为、实际行为、错误信息

**场景 3：性能问题**
- 错误：直接优化代码，不知道瓶颈在哪
- 正确：提问确认卡顿的操作、发生频率、浏览器性能监控数据

#### 用户回答后的处理

1. **仔细分析用户的回答**，提取关键信息
2. **总结给用户**："明白了，问题的核心是 [总结]"
3. **提出解决方案**："基于这些信息，我认为问题可能是 [分析]，建议 [方案]"
4. **实施后验证**："请测试，如果还有问题，请告诉我具体现象"

#### 避免的提问方式

❌ **不要问模糊的问题**：
- "是不是有什么问题？" （太宽泛）
- "能详细说说吗？" （没有具体指向）
- "你确定吗？" （质疑用户描述）

✅ **要问具体、可回答的问题**：
- "偏移的是哪几个元素？" （具体）
- "是向左还是向右偏移？" （可选择的答案）
- "偏移大概多少像素？" （可量化的）

---

**核心原则**：代码是写给人看的，其次才是给机器执行。保持简洁、清晰、易读。
