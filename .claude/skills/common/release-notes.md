# 发行版文案指南

## 适用场景

用户要发新版本（vX.Y.Z Release），需要写标题和内容时。

## 写前必做（顺序不可省）

1. **全量核对提交**：`git log <上个tag>..HEAD --oneline`，以提交记录为唯一事实源——禁止凭记忆或旧文档归纳"这个版本做了什么"
2. **核实描述性事实**：涉及现状描述（设计风格、架构、界面）必须与当前代码/最新文档核对——旧文档可能过时（实证：凭过时 design-system.md 写了"宣纸风"，实际早已改冷灰，被用户纠正）
3. **核实数字口径**：性能数字写前查来龙去脉（实证：把"中途探索膨胀到 46MB 又回退"错写成"46MB→23MB 优化减半"——基线本来就在 23MB）

## 写作三原则（用户定版原话）

- **通俗易懂**：写使用者能感知的东西，说人话
- **写重点**：每条一句话讲清"是什么、有什么用"
- **不乱加形容词**

## 禁止清单（AI 味）

| 禁止 | 示例（❌ → ✅） |
|------|------|
| 堆砌形容词 | ❌ 全新 / 焕新 / 重磅 / 赋能 / 极致 / 优雅 / 强大 → ✅ 重写、新增、修复、改为 |
| emoji 分节 | ❌ 🌟核心新特性 ✨新功能 🐛修复 → ✅ 纯文字标题分节 |
| 夸大叙事 | ❌ "性能优化 200%" → ✅ "构建产物保持在 23MB 左右" |
| 凑数条目 | 内部重构、死代码清理、依赖升级——使用者无感知 → 不写，或全篇末尾一句"内部代码清理"带过 |
| 空泛技术词 | ❌ 现代化技术栈 → ✅ Nuxt 3 + TypeScript + Naive UI |

## 结构模板

### 大版本（有整块功能重写/界面改版）

```
标题：动词短语直说最大变化（例：重写管理后台，门户界面改版）

## <大功能名>
一段话：旧的是什么 → 这次做了什么；能力覆盖用列表

## <第二大变化>（如有）
## 新功能（一条一件事）
## 性能与部署
## 接口变更（二次开发需注意）
```

### 小版本

```
标题：一句话说最主要的变化
## 新功能
## 修复
## 其他
```

## 条目写法

- **功能条目** = 是什么 +（用途 / 前后对比），一行读完：
  - ✅ 系统消息支持发送给指定用户（原来只能群发）
  - ✅ 首页侧栏热门文章榜
  - ❌ 全新的消息系统赋能精细化运营
- **破坏性变更必须单独成节**（接口方法/参数格式变化、删除的接口）：二次开发者看不到代码也会升级，放显眼位置并标注适用对象
- **分节按使用者视角排序**：直接看到/用到的最前，内部改进最后

## 检查清单

- [ ] 每条都来自 git log 核对，没有凭记忆写的？
- [ ] 现状描述（风格/架构/数字）核对过最新代码或文档？
- [ ] 全文没有 emoji、没有"全新/焕新/重磅"类形容词？
- [ ] 使用者无感知的内部改进没有单独成条？
- [ ] 破坏性接口变更有独立小节？
- [ ] 每条一行读完能懂？
