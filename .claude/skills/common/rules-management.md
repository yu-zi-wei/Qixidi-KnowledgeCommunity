# Rules 管理指南

## Rules 目录结构

```
.claude/rules/
├── common/                 # 通用规则
│   ├── architecture.md     # 系统架构设计
│   └── code-basics.md      # 通用编码规范
├── frontend/               # 前端规则
│   ├── qixidi-web-nuxt3.md # Nuxt 3 开发规范
│   └── global-component-management.md  # 全局组件状态管理
└── backend/                # 后端规则
    └── qixidi-service.md  # Spring Boot 开发规范
```

## 各 Rule 文件职责

### 通用规则（所有项目）

| 文件 | 职责 | 适用对象 |
|------|------|----------|
| `rules/common/architecture.md` | 前后端架构设计、分层架构、模块划分 | 架构设计 |
| `rules/common/code-basics.md` | 命名规范、注释规范、错误处理规范、类型安全 | 所有代码编写 |

### 前端规则（Nuxt 3）

| 文件 | 职责 | 适用对象 |
|------|------|----------|
| `rules/frontend/qixidi-web-nuxt3.md` | Nuxt 3、SSR/CSR、主题切换、API 调用、组件规范 | 前端开发 |
| `rules/frontend/global-component-management.md` | 全局组件状态管理（弹窗、对话框等） | 前端开发 |

### 后端规则（Spring Boot）

| 文件 | 职责 | 适用对象 |
|------|------|----------|
| `rules/backend/qixidi-service.md` | Spring Boot、MyBatis Plus、MVC 分层、事务管理、日志 | 后端开发 |

## 编写原则

### 核心原则
- **通用性**：规则必须通用，不绑定具体业务模块
- **文字描述**：用文字描述规范为主，单行示例为辅
- **简洁明了**：只保留核心信息，避免冗余
- **表格化**：能用表格说明的不要用大段文字
- **稳定可维护**：避免频繁更新，不列出具体业务模块列表

### 禁止事项
- ❌ 不要写具体业务代码示例
- ❌ 不要绑定具体业务模块（如"文章模块"、"用户模块"）
- ❌ 不要使用具体业务名称作为示例（如"文章标题"应改为"数据标题"）
- ❌ 不要写大片的代码案例（多行完整代码块）
- ❌ 不要写可以推断出来的内容
- ❌ 不要在 Rules 中列出具体业务模块清单（应在 INDEX.md 中维护）

### 关于代码示例
- ✅ **允许**：单行简短示例，如 `@NotNull(groups = Update.class)`、`b_` 前缀
- ✅ **通用示例**：使用通用名称（如 `XxxController`、`dataName`），避免具体业务名称
- ✅ **技术示例**：可以使用技术栈相关示例（如 `useArticleApi`、`ArticleService`）
- ❌ **禁止**：多行完整代码块、完整类/方法定义
- ❌ **禁止**：使用具体业务模块名称作为通用示例（如 `ArticleController`、`文章标题`作为命名示例）

### 维护性原则
- ✅ **稳定优先**：Rules 应尽量稳定，避免每次新增业务模块都需要更新
- ✅ **分离关注点**：具体业务模块列表应在 `INDEX.md` 中维护，不在 Rules 中
- ✅ **通用示例**：代码示例应使用通用名称，便于理解且不绑定具体业务

## 编写流程

### 新增 Rule 文件

1. **确认需求**：确定需要规范的内容是否已有 Rule 涵盖
2. **检查现有规则**：查看是否可以更新现有 Rule 而不是新建
3. **确定文件名**：使用简短的英文命名，如 `code-basics.md`、`framework.md`
4. **按模板编写**：参考现有 Rule 的格式和风格，使用通用示例
5. **更新本文档**：将新增的 Rule 加入"各 Rule 文件职责"表格
6. **更新 README.md**：判断是否需要同步更新 .claude/README.md（通常不需要）

### 更新 Rule 文件

1. **确认变更范围**：明确本次更新的内容范围
2. **保持风格一致**：参考现有 Rule 的格式和风格
3. **文字为主**：用纯文字描述，避免大片代码案例
4. **检查重复**：避免与其他 Rule 内容重复
5. **检查示例**：确保示例使用通用名称，不绑定具体业务
6. **更新 README.md**：判断是否需要同步更新 .claude/README.md（通常不需要）
7. **记录变更**：在回答结束后展示变更内容

## Rule 文件结构模板

### 推荐结构
```markdown
# [规则名称]

## [分类1]
### [子分类]
- 规则1
- 规则2

## [分类2]
### [子分类]
- 规则1
- 规则2

## 通用规范
| 场景 | 处理方式 |
|------|----------|
```

### 示例风格
```markdown
# 命名规范

## 类名后缀
| 类型 | 后缀 | 示例 |
|------|------|------|
| 控制器 | `Controller` | `XxxController` |

## 方法名
使用小驼峰，动宾结构。

## 数据库
使用小写+下划线，带 b_ 前缀。
```

**注意**：示例中使用 `Xxx` 作为通用前缀，避免使用具体业务名称。

## 更新检查清单

每次更新 Rule 后，检查以下问题：

- [ ] 是否避免了大片的代码案例？
- [ ] 是否用表格替代了大段文字？
- [ ] 是否去掉了具体业务引用？
- [ ] 是否使用通用名称作为示例？
- [ ] 是否与其他 Rule 有重复？
- [ ] 风格是否与现有 Rule 一致？
- [ ] 是否避免了列出具体业务模块清单？
- [ ] 更新后是否需要频繁修改？

## 维护说明

本文档随 Rules 的增删实时更新。每次新增或修改 Rule 时，必须更新"各 Rule 文件职责"表格。

**更新完成后必须在回答结束后展示变更内容。**

**注意**：更新 .claude/ 下的任何文件时，应判断是否需要同步更新 README.md。

**核心原则**：Rules 应保持稳定，避免因新增业务模块而频繁更新。具体业务模块的列表和路由信息应在 `skills/INDEX.md` 中维护。
