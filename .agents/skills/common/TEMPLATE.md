# Skill 编写规范

## 编写原则补充

### 高内聚原则
- **独立描述**: 每个 Skill 只描述自己的模块，不与其他模块进行对比
- **避免跨模块比较**: 不要包含"与商品模块差异"、"与订单模块对比"等内容
- **职责清晰**: 明确模块负责什么、不负责什么，不要描述其他模块的功能

### 维护性原则
- **稳定可维护**: 避免在 Skill 中列出其他模块的清单
- **路由在 INDEX**: 模块间的路由关系应在 `INDEX.md` 的 Skill Router 中维护

## 面向对象
本 Skill 是给**其他业务模块的 AI 开发**看的，相当于这个业务的"API文档"或"说明书"。

## 编写原则

1. **以描述为主**：用文字描述，单行示例为辅
2. **面向调用者**：从"其他模块如何调用这个模块"的角度编写

### 内容编写原则

**核心原则**: Skill 只写大模型可能不清楚的内容，项目里有的内容简单介绍引导大模型自己读。

#### 3.0 命名规范
- **目录和文件名**: 使用小写短横线命名（kebab-case），如 `article-module/article.md`
- **描述中的关键词**: 使用自然语言描述，便于阅读
- **错误示例**: `ArticleModule/`、`ArticleModule.md`（避免大写和驼峰）

#### 3.1 实体字段
- ❌ **不要列出详细字段表格**
- ✅ **只写**：实体名称、路径、关键字段（2-3个）
- ✅ **引导语**: "具体字段查看实体类注释"

#### 3.2 状态定义
- ❌ **不要列出状态值表格**
- ✅ **引导语**: "状态字段的具体值查看实体的 @see 注解"
- ✅ 如果没有 @see 注解，引导大模型去看业务逻辑然后补全 @see

#### 3.3 Controller 方法
- ❌ **完全不要列出 Controller 方法表格**
- 理由：Controller 是对外接口，业务逻辑不需要去看 Controller
- ✅ **只写**：Controller 名称和路径即可

#### 3.4 ApplicationService 方法
- ❌ **不要列出方法表格**
- ✅ **只写**：ApplicationService 的职责说明
- ✅ 如果大模型需要，引导它自己去阅读 ApplicationService 文件

#### 3.5 通用方法
- ❌ **不要列出所有方法**
- ✅ **只写**：核心的、大模型可能不清楚的查询方法（2-5个）
- ✅ **引导语**: "更多方法查看 XxxDomainService 接口定义"

#### 3.6 9. AI 开发 Workflow
- ❌ **不要写具体的 Controller 方法名**（如 `DemandInfoController.add`）
- ✅ **写法**: "定位 Controller 层的新增接口" 或 "定位新增接口"
- 理由：Controller 方法名可能变化，而且大模型可以自己找到

## 编写流程

1. **分析需求**：理解模块的职责和边界
2. **读取代码**：查看 Controller、DomainService、Entity
3. **提取核心**：总结核心字段、业务规则、通用方法
4. **按模板编写**：严格按照模板结构编写
5. **检查遗漏**：确认是否所有必需段落都已填写

## 更新规范

### ⚠️ 强制要求

**每次新增或更新 Skill 时，必须执行以下检查：**

1. **检查通用规范**：回顾本次编写过程，总结是否有新的通用规范需要写入本模板
2. **更新模板**：如发现新的通用规范，必须更新本模板
3. **更新 README.md**：更新 .claude/ 下的任何文件时，判断是否需要同步更新 README.md
4. **展示变更**：对于 TEMPLATE.md 或 README.md 的任何变更，必须在回答结束后以清晰的格式展示出来

**⭐ 编写代码时的强制检查**：

**后端开发**：
- [ ] **是否在循环中调用数据库？**（严重违反架构规则）
- [ ] **ApplicationService 是否直接调用 Repository？**（禁止！必须通过 DomainService）
- [ ] **是否优先复用了现有方法？**（不要第一时间写新查询）
- [ ] **业务逻辑是否放在了正确位置？**（站在业务模块的全局视角，不要只看当下）
- [ ] **是否理解了现有设计意图？**（不要轻易改变架构设计）
- [ ] **返回类型是否匹配？**（检查方法签名，不要想当然）
- [ ] **是否混淆了 Entity 和 Vo？**（Repository 返回 Entity，Service 转换为 VO）
- [ ] **实体类是否同时使用了 @Data 和 @NoArgsConstructor？**（必须）
- [ ] **新增/更新/删除是否加了 @Log 注解？**（必须）
- [ ] **是否违反了其他 Rules？**（architecture.md, code-basics.md, qixidi-service.md）

**前端开发**：
- [ ] **是否在 SSR 代码中使用了客户端专用 API？**（如 useMessage、useDialog）
- [ ] **颜色是否使用了 CSS 变量？**（禁止硬编码颜色值）
- [ ] **是否支持深色模式？**（切换主题测试）
- [ ] **组件是否过度拆分？**（复用 < 2 次或逻辑简单不应抽取）
- [ ] **是否使用了正确的 API 调用方法？**（分页用 getPage，非分页用 get/post/put/delete）
- [ ] **是否违反了其他 Rules？**（architecture.md, code-basics.md, qixidi-web-nuxt3.md）

**质量 > 速度**：多花时间理解业务，少花时间反复修改。

**如果违反任何 Rule，必须立即修正，不能等到用户指出。**
